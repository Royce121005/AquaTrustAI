# AquaTrust AI — Dataset Portfolio and Source-Agnostic Data Strategy

**Status:** AUTHORITATIVE / FROZEN — v2.2.1
**Scope:** Dataset selection, provenance, preprocessing, simulator inputs and reproducibility

## 1. Purpose

AquaTrust AI does not depend on one permanent wastewater dataset. The project uses a **versioned, provenance-controlled dataset portfolio**. Public source datasets may change or be replaced after an explicit Phase 2 audit without requiring changes to the canonical domain model, simulator interface, API, validation, AI, compliance, cryptography or DLT layers.

The dataset layer is therefore replaceable; the canonical data contract and trust pipeline are not.

## 2. Current source strategy

The initial research source pool is:

1. **UCI Water Treatment Plant** — official UCI Machine Learning Repository dataset. It contains daily sensor measurements from an urban wastewater treatment plant and is suitable as a historical ML/data-quality source. It is not evidence of current plant operating conditions and must be treated as a historical benchmark source. Official source: https://archive.ics.uci.edu/dataset/106/water%2Btreatment%2Bplant
2. **Melbourne Water Eastern Treatment Plant (ETP) inlet/outlet wastewater-quality datasets** — official DataVic/Melbourne Water open-data sources containing selected wastewater quality parameters. The inlet and outlet datasets have different sampling contexts; date equality does not establish that two rows are one synchronized treatment event. Official source family: https://discover.data.vic.gov.au/organization/melbourne-water-corporation
3. **Selected CPCB sewage-treatment-plant performance evaluation reports** — official Central Pollution Control Board reports containing plant/stage observations. Reports are heterogeneous and may contain measured values, standards/limits and narrative text; extraction must classify these record types before canonicalization. The exact report URL, retrieval date, document identity and extracted records must be recorded in the dataset manifest for every report actually used.

These are an approved **source pool for Phase 2 auditing**, not a claim that every source must be used in every experiment. Phase 2 must select the final dataset snapshot based on parameter coverage, provenance, licensing/reuse conditions, quality, temporal structure and suitability for the frozen research objectives.

## 3. Legacy repository datasets

The previously bundled Bangalore STP dataset and Indian water-quality reference dataset are retained as **legacy/current-state assets** for repository audit, migration/regression comparison and provenance review.

They are **not frozen as the permanent master research dataset**.

Agents must not:
- delete them merely because the source strategy changed;
- silently treat them as the final research dataset;
- build new backend interfaces that are hard-coded to their filenames;
- represent legacy records as live physical sensor telemetry.

## 4. Non-negotiable dataset rules

### 4.1 No source-specific backend contracts

Backend services must consume the canonical wastewater reading contract. Dataset-specific column names, filenames and source formats belong only inside dataset adapters/preprocessing.

### 4.2 No row-wise merging of unrelated sources

Records from different physical facilities, studies or source datasets must not be combined into one synthetic observation merely to fill missing parameters.

For example, a COD value from UCI and an ammoniacal-nitrogen value from Melbourne must not be joined and represented as though both were measured during the same treatment event.

Cross-source data may be used for distributional analysis, parameter-specific training, simulation inputs or controlled experiments only when the methodology explicitly supports that use.

### 4.3 Observed versus simulated provenance

Every record must distinguish whether it is:

- `observed` — originating from a public/real source observation; or
- `simulated` — generated by the AquaTrust simulator.

Simulation must preserve the source dataset lineage used to construct the simulation input.

### 4.4 Treatment-stage semantics are preserved

Where a source distinguishes inlet, intermediate treatment or final-effluent sample points, Phase 2 must map that meaning to the canonical `treatment_stage` field.

Never infer `final_effluent` merely because a row is the last row in a report or because a parameter name appears in an outlet section without verified source semantics.

### 4.5 Missing parameter coverage is explicit

A dataset is not required to contain all six core parameters. Missing coverage must be represented explicitly and must not be fabricated through cross-source row-wise joins.

The core AI parameters remain:

- BOD
- COD
- TSS
- pH
- ammoniacal nitrogen
- total nitrogen

### 4.6 Dataset snapshots are immutable experiment inputs

Once an experiment starts, its dataset portfolio manifest, source checksums, processed-data checksums, transformation configuration and simulator seed are frozen for that experiment run.

## 5. Source-record classification

The portfolio manifest must classify extracted source records as `measurement`, `regulatory_limit` or `narrative_or_metadata`. Only `measurement` records can enter the canonical observed-reading pipeline.

## 6. Canonical lineage

```text
source dataset
    ↓
dataset adapter / preprocessing
    ↓
canonical standardized records
    ↓
simulator input / direct analysis
    ↓
facility + sensor + reading
    ↓
validation
    ↓
anomaly detection
    ↓
compliance
    ↓
treatment record
    ↓
certificate
    ↓
hash + signature
    ↓
PostgreSQL evidence + Fabric anchor
```

Every stage must preserve enough provenance to reconstruct the lineage.

## 7. Dataset manifest requirements

Each source dataset must have a manifest containing at minimum:

- `dataset_id`
- `dataset_name`
- `source_name`
- `source_reference`
- `retrieval_date`
- `license`
- `original_filename`
- `source_sha256`
- `processing_version`
- `processing_timestamp`
- `transformations_applied`
- `excluded_record_count`
- `exclusion_reasons`
- parameter coverage
- unit mapping
- timestamp semantics
- facility/stage semantics
- known limitations
- `data_origin`

Agents must never invent missing provenance. Unknown values remain explicitly unknown until verified.

## 8. Dataset-to-simulator boundary

The simulator receives standardized records or approved parameter distributions produced by the dataset pipeline. It must not parse source-specific CSV/XLSX/PDF formats directly.

```text
UCI / Melbourne / CPCB / legacy sources
                 ↓
          Phase 02 adapters
                 ↓
        canonical processed data
                 ↓
             Phase 03
          multi-STP simulator
```

## 9. Dataset replacement rule

A dataset can be replaced or supplemented without changing the downstream architecture when all of the following remain stable:

- canonical reading semantics;
- parameter vocabulary;
- unit normalization rules;
- timestamp semantics;
- provenance requirements;
- simulator input contract;
- experiment methodology.

A change that affects those frozen semantics requires `MASTER/CHANGE_CONTROL.md` and an approved change record.

## 10. Phase 2 selection gate

Before a source is used as an authoritative experiment input, Phase 2 must verify:

1. source identity;
2. download/retrieval method;
3. checksum;
4. license/reuse conditions;
5. parameter mapping;
6. units;
7. timestamp semantics;
8. facility/stage semantics;
9. missingness and quality issues;
10. transformation reproducibility;
11. suitability for the intended ML/simulation use;
12. limitations and exclusions.

The resulting `dataset_manifest` is the authoritative record of what data was actually used.

## 11. Agent rule

If a new dataset appears during implementation:

- do not silently replace the current approved source pool;
- audit it through the Phase 2 process;
- record provenance;
- preserve source checksums;
- update the dataset manifest;
- use change control if the new source changes a frozen contract or research methodology.
